**Goal:** Editar el cuadro de Esterilización en el navegador con el mismo registro de cambios que Qt (permuta / cambio de servicio / ajuste), con control de revisiones, auditoría y anulación.

**Architecture:** Un módulo nuevo `an/web/rutas_edicion.py`: cada escritura de un periodo pide `If-Match: <revision>`, bloquea la fila con `SELECT … FOR UPDATE`, llama a `cambios.*`/`flujo.*` del núcleo, sube `periodo.revision` y responde las alertas nuevas. La transacción por petición ya la da `contexto_area` (una excepción HTTP deshace todo). La auditoría de cada escritura ya la hace el middleware (`auditoria`: método, ruta, código); la ruta solo le pone `request.state.evento`. Front: la `Planilla` gana selección y arrastre; un diálogo «Registrar cambio» conserva lo escrito ante 409 y 401.

**Tech Stack:** FastAPI, psycopg 3, PostgreSQL con RLS, pytest; React 19 + TS.

**Spec:** `docs/PLAN_WEB.md` §4 («Edición con revisión») y §6 Fase 5; paridad con `an/turnos/paginas.py` y `tests/esterilizacion/test_cambios.py`.

## Decisiones

- **Periodos solapados (hallazgo de la base migrada: `2026-11-01/2026-11-30` y `2026-11-02/2026-11-29`).** La API **rechaza con 409** crear un periodo que se solape con otro del área (`POST …/periodos`, Tarea 5): dos cuadros sobre las mismas fechas dejan a una persona con dos turnos el mismo día y `asignaciones_rango` (descanso entre periodos) los mezcla. `generar` no crea periodos, así que no necesita la comprobación. No se agrega restricción en la base: la migrada ya tiene un solapamiento y una restricción la haría fallar; se anota para que la coordinación decida cuál borrar o cerrar. Tarea 5 deja además `GET …/periodos` con el campo `solapa_con` (lista de ids) para que el front lo muestre.
- **`periodo_cerrado` del núcleo lee `periodo_estado`; la API lee `periodo.cerrado_en`.** Cerrar/reabrir escribe las dos (el núcleo manda; `periodo.cerrado_en` es su espejo para listar).
- **«Quién cambió»** para el 409: columnas nuevas `periodo.modificado_por text` y `modificado_en timestamptz` (migración 007), escritas en cada subida de revisión de la API. El trabajador del solver no las escribe (la generación no es una edición manual): el 409 dirá «Alguien» si están vacías.
- **Paridad con Qt dejada fuera de PR 1** (se anota en PR 2 la lista final): deshacer con Ctrl+Z (la web tiene Anular en la pestaña), vista «Original» (solo lectura), edición por escritura directa en la celda (se usa el diálogo), exportar (Fase 6), banco de horas (fuera de la lista de la fase), cuadro por semanas con selector de modo (la web abre periodos existentes).
- **Edición en lote:** una sola fila `ajuste` para todas las celdas (como Qt). Tope 400 celdas por petición.
- **Celdas editables:** como `_editable` de Qt: persona con `en_solver`, fecha dentro del periodo, periodo no cerrado, y no una celda libre cubierta por novedad. Código `L` o un turno del catálogo.
