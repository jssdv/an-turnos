**Goal:** Generar un periodo desde la API sin bloquearla: la API encola un `trabajo`, un proceso trabajador corre el solver con progreso y cancelación, y guarda el cuadro solo si el periodo no cambió.

**Architecture:** `solver.generar` gana `al_avance` (callback de soluciones) y `detener` (`threading.Event` que un hilo vigía convierte en `stop_search()`). La cola es la tabla `trabajo` (índice único parcial por clínica). El trabajador toma con una función `SECURITY DEFINER` (`FOR UPDATE SKIP LOCKED`) porque aún no conoce la clínica; desde ahí trabaja con el alcance RLS de esa clínica/área. Mientras el solver corre en el hilo principal, un hilo monitor escribe progreso (≤ 1/s), latido (5 s) y lee `cancelar` (1/s).

**Tech Stack:** Python 3.13, OR-Tools 9.15 CP-SAT, PostgreSQL 16 (Docker, puerto 5433), psycopg 3, FastAPI, pytest.

**Spec:** `docs/PLAN_WEB.md` (§2 «Cambios al núcleo», §3 `trabajo`, §4 «Trabajador», §6 Fase 3, §8)

  - `marcar_huerfanos() -> int` (llama `app_marcar_fallidos(latido_max)`),
  - `correr_uno() -> bool` (toma un trabajo y lo ejecuta de punta a punta; `False` si no había),
  - `servir(parar: threading.Event)` (marca huérfanos al arrancar y cada `revisar_cada`; si `correr_uno()` da `False`, espera `sondeo`),
  - `main()` (pool de `abrir_pool()` con `AN_PG_URL`/`AN_ROL`; SIGTERM/SIGINT activan `parar`; lee `AN_TRABAJADOR_LATIDO_CADA`, `AN_TRABAJADOR_LATIDO_MAX`, `AN_TRABAJADOR_PROGRESO_CADA` opcionales).
- Formato de `params` (lo escribe la ruta de Task 4): `{"modo": "cero"|"respetar"|"semana", "lunes": "AAAA-MM-DD"|null, "tiempo": int, "semilla": int}`.
- Formato de `resultado` en `listo`: `{"estado": <StatusName>, "objetivo": float, "faltan": [["AAAA-MM-DD", tramo, n], …], "solicitudes": [{"id": int, "estado": "parcial"|"no cumplida", "motivo": str}, …]}`.
- Formato de `progreso`: el dict de `al_avance` más `"estado": "buscando"`.

Flujo de `correr_uno` (cada paso con su transacción y alcance de la clínica/área del trabajo): tomar → arrancar hilo monitor (ya con `detener`) → leer clave del periodo y `flujo.preparar` → `solver.generar(ctx, dias, al_avance=…, detener=…, semilla=…, **kw)` en el hilo principal (el callback solo guarda el último dict) → parar el monitor → resolver: si `detener` activo → `cancelado` sin escribir; si `ErrorSolver` → `fallido` con su mensaje; otra excepción → `fallido` «Error interno» y `log.exception`; si no, una sola transacción: `SELECT revision FROM periodo WHERE id = ? FOR UPDATE`; si ≠ `revision_base` → `conflicto` (mensaje «El periodo cambió mientras se generaba; vuelve a generar.») sin escribir; si no, `flujo.terminar`, `UPDATE periodo SET revision = revision + 1`, `listo` con `resultado`. Todo `UPDATE` de estado final lleva `WHERE estado = 'corriendo'` y pone `terminado = now()`. El monitor, cada `sondeo_monitor` = 1 s: lee `cancelar` (si es verdadero activa `detener`), escribe `progreso` solo si cambió desde la última escritura, y escribe `latido` cada `latido_cada`.
